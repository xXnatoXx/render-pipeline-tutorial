Modern Graphics APIs

Everything so far happened on the GPU. This chapter is about the conversation that gets it there: how your program describes work, and why Vulkan, Direct3D 12, Metal and WebGPU ask you to say so much more than OpenGL ever did.

A short family tree

A graphics API is a contract between your program and the GPU driver. The first popular one, IRIS GL, ran on Silicon Graphics workstations in the 1980s. SGI opened it up as OpenGL in 1992. Microsoft answered with Direct3D in 1996. Phones got OpenGL ES and browsers got WebGL. Then, in the 2010s, a new family appeared. AMD's Mantle (2013) showed that a thinner, more explicit API could cut CPU cost dramatically, and it was followed by Metal (2014), Direct3D 12 (2015), Vulkan (2016, built on Mantle's foundations) and finally WebGPU for the web.

STEP 1A global state machine vs explicit objects

OpenGL is a state machine. There is one hidden "current state" per context: the current program, the bound vertex array, which texture sits on each texture unit, whether blending is on, and hundreds more switches. Every call like glBindTexture or glEnable just flips one of those switches. Nothing is checked until you call glDrawArrays. Only then does the driver look at the whole state and work out what the GPU must actually do.

This is easy to start with, and it is the root of OpenGL's problems. State "leaks" from one draw into the next. The driver must re-check everything on every draw. And because the final GPU configuration is only known at draw time, the driver sometimes has to compile a shader variant right then, in the middle of your frame.

Explicit APIs replace the global state with objects you build up front. You create a device, bake a pipeline containing shaders and fixed-function settings, group resources into a bind group, record commands into a command buffer, and submit it to a queue. Each object is validated once, when you create it.

Key idea. OpenGL asks "what is the state right now?" at every draw. Explicit APIs ask "which pre-built object do you want?" The work of checking and compiling moves from draw time to load time, where you control it.

STEP 2Where the CPU time goes

Picture a scene with 3,000 draw calls. In OpenGL, each draw costs the driver a few microseconds of validation, hazard tracking (does this texture still have pending writes?) and translation into GPU commands. At 3 µs per draw that is 9 ms, more than half of a 16.6 ms frame, and it all happens on the one thread that owns the GL context. Some drivers move part of it to a hidden worker thread, but you can't control that.

Worse is the hitch. When a draw uses a state combination the driver hasn't seen before, it may need to compile or patch a shader on the spot. That can take tens of milliseconds, and the player sees a stutter.

In an explicit API, recording a draw is cheap because the pipeline was already validated and compiled. Better still, command buffers can be recorded on many threads at once, and the main thread just submits them to the queue.

Key idea. Explicit APIs don't make the GPU faster. They make the CPU side cheaper and parallel, and they let you compile pipelines at load time. Forget to pre-build a pipeline and an explicit API will hitch too; the difference is that it is now your choice when that cost is paid.

STEP 3Frames in flight, fences and semaphores

The CPU and GPU are two separate processors. If the CPU waited for the GPU to finish every frame before starting the next, each would sit idle half the time. So engines keep several frames in flight: while the GPU draws frame N, the CPU is already recording frame N+1.

That raises a safety question. Each frame writes into its own copy of per-frame data (a uniform buffer of camera matrices, a command buffer). Before the CPU reuses frame slot 0, it must know the GPU has finished reading it. That is what a fence is for: the GPU signals it when a submission completes, and the CPU waits on it (vkWaitForFences, ID3D12Fence). A semaphore is the GPU-to-GPU version: "don't start rendering until the swapchain image is acquired", "don't present until rendering is done". The CPU never waits on those.

Key idea. More frames in flight hide CPU/GPU hiccups and keep both processors busy, but each extra frame adds latency. Two is the common default; three smooths out spiky workloads.

STEP 4Barriers and layout transitions

GPUs run thousands of threads, out of order, through layers of caches. A texture you just rendered may still be half in flight, sitting in a cache, or stored in a compressed layout that only the render-target hardware understands. OpenGL's driver tracks all this for you. Vulkan and Direct3D 12 make you say it with a barrier: "wait until writes from the color-output stage finish, make them visible, then convert the image into a layout the texture sampler can read".

In Vulkan, a barrier recorded with vkCmdPipelineBarrier also performs an image layout transition, such as COLOR_ATTACHMENT_OPTIMAL → SHADER_READ_ONLY_OPTIMAL, and later the swapchain image goes to PRESENT_SRC_KHR. Direct3D 12 does the same with ResourceBarrier and states like D3D12_RESOURCE_STATE_RENDER_TARGET → D3D12_RESOURCE_STATE_PIXEL_SHADER_RESOURCE → D3D12_RESOURCE_STATE_PRESENT. Metal and WebGPU track most hazards automatically.

Key idea. A barrier is a promise about ordering and visibility: "these writes happen before those reads." Leave one out and the bug is timing-dependent. It may look fine on your GPU and flicker on another. The validation layers (Vulkan) and debug layer (D3D12) catch many of these.

STEP 5Same scene, different conventions

This tutorial uses OpenGL's clip space, where NDC depth runs from −1 at the near plane to +1 at the far plane. Direct3D, Vulkan, Metal and WebGPU all use z ∈ [0, 1] instead, so their projection matrices are slightly different. Vulkan has a second trap: its NDC y axis points down, so y = −1 is the top of the image. Feed Vulkan an OpenGL projection matrix unchanged and the picture comes out upside down, with the closest part of the scene clipped away. The usual fixes are to flip the sign of the y scale in the projection matrix, or to use a negative viewport height (allowed since Vulkan 1.1).

Many modern engines also use reverse-Z: map the near plane to 1 and the far plane to 0. Floating-point numbers are densest near zero, and that density cancels out the way perspective crowds distant depths together. The result is far less z-fighting in the distance.

About shading languages: GLSL belongs to OpenGL, HLSL to Direct3D, MSL (C++-based) to Metal and WGSL to WebGPU. Vulkan's driver doesn't read source text at all. It consumes SPIR-V, a binary intermediate representation that you compile offline from GLSL or HLSL. Tools such as SPIRV-Cross and Tint translate between these, which is how one engine's shaders reach every API.

Key idea. The concepts are the same across all four explicit APIs; only the names change. Learn one well and the others become a translation exercise. Just watch the depth range and the y direction.

STEP 6Hello triangle, three ways

Here is the smallest program that puts one orange triangle on screen. In OpenGL, most of the setup is loose state that only comes together at glDrawArrays. In WebGPU, the setup builds one pipeline object, and each frame records a command buffer and submits it. The Vulkan version shows only the call sequence, because the full program, with every create-info struct filled in, runs to several hundred lines. Error handling and window creation are left out everywhere.

The Direct3D 12 and Metal versions have the same shape. You create a device and queue, build a pipeline state, record into an ID3D12GraphicsCommandList (ending in DrawInstanced(3, 1, 0, 0)) or an MTLRenderCommandEncoder (ending in drawPrimitives:vertexStart:vertexCount:), then execute or commit it on the queue.

Key idea. Explicit code is longer, but the extra lines are mostly one-time setup. The per-frame part, "record, submit, present", stays short, predictable and parallel-friendly.

RECAPWhat to remember

  • Lineage: IRIS GL → OpenGL (1992) → OpenGL ES / WebGL; Direct3D alongside; Mantle (2013) inspired Metal (2014), Direct3D 12 (2015) and Vulkan (2016); WebGPU shipped in Chrome in 2023.
  • OpenGL is a global state machine. The driver validates, tracks hazards and sometimes compiles shaders at draw time, which costs CPU and causes hitches.
  • Explicit APIs use objects: device and queue, pipeline state objects baked ahead of time, descriptor sets / root signatures / argument buffers / bind groups for resources, and command buffers recorded on many threads.
  • Synchronization is your job: fences let the CPU wait for the GPU, semaphores order GPU work, and barriers (with layout transitions) order writes before reads.
  • Frames in flight (usually 2–3) keep CPU and GPU both busy; each extra frame adds latency.
  • Conventions: depth is [0, 1] in D3D/Vulkan/Metal/WebGPU and [−1, 1] in OpenGL; Vulkan's NDC y points down; reverse-Z improves depth precision.
  • Shaders: GLSL, HLSL, MSL and WGSL are source languages; SPIR-V is the intermediate form Vulkan consumes.

Further reading: the Vulkan specification, WebGPU and WGSL at the W3C, and Microsoft's Direct3D 12 programming guide.

Rasterization & Depth

After the vertex stage, a triangle is just three points on the screen. The rasterizer works out exactly which pixels it covers, blends the vertex data across them, and, with the depth buffer, decides which surface you actually see.

STEP 1From three vertices to a set of pixels

The vertex shader outputs one position per vertex in clip space (chapter 01). Primitive assembly then groups those vertices into primitives: every three indices of a triangle list form one triangle. Each triangle goes through a few checks before any pixel is touched.

The first check is clipping. A point is inside the view volume when −w ≤ x, y, z ≤ w in clip space. The side planes are easy to handle, but the near plane is essential. For a perspective camera, w = −zview, the distance in front of the camera. A vertex behind the camera has w ≤ 0, and dividing by it flips the signs of x/w and y/w. That vertex lands on the wrong side of the screen and the triangle smears across the view. So the triangle is cut against z = −w (the near plane) before the perspective divide. Cutting one corner off a triangle leaves a quadrilateral, which is split back into two triangles.

Clipping against the four side planes is more expensive than it is useful, so many GPUs use a guard band: a region much larger than the viewport where the rasterizer can still work with its fixed-point math. A triangle that pokes outside the viewport but stays inside the guard band is not cut up. The rasterizer simply never visits the pixels outside the viewport (a scissor test). Only triangles that cross the near plane, or reach past the guard band, need real geometric clipping.

After clipping comes the perspective divide, the viewport transform and triangle setup. Setup computes everything the rasterizer needs per triangle: the edge equations, the bounding box and the triangle's signed area. The sign of the area gives the winding, which is what back-face culling uses to drop triangles that face away. Then the rasterizer answers one question for every pixel in the bounding box: is the pixel's center inside the triangle?

Key idea. A pixel is not covered "a bit". With one sample per pixel, coverage is a yes/no test at a single point, the pixel center. Everything the rasterizer outputs is a set of these yes/no decisions, called fragments.

STEP 2Edge functions: the inside test

How does a GPU test "is this point inside the triangle" millions of times per frame? It uses one small formula per edge. For a directed edge from a to b, the edge function of a point p is a 2D cross product:

edge⁡(a,b,p)=(bx−ax)(py−ay)−(by−ay)(px−ax)E0(p)=edge⁡(v1,v2,p)←the edge opposite v0E1(p)=edge⁡(v2,v0,p)←the edge opposite v1E2(p)=edge⁡(v0,v1,p)←the edge opposite v2inside  ⟺  E0(p)≥0  and  E1(p)≥0  and  E2(p)≥0\begin{aligned} \operatorname{edge}(a, b, p) &= (b_x - a_x)(p_y - a_y) - (b_y - a_y)(p_x - a_x)\\[8pt] E_0(p) &= \operatorname{edge}(v_1, v_2, p) && \leftarrow \text{the edge opposite } v_0\\ E_1(p) &= \operatorname{edge}(v_2, v_0, p) && \leftarrow \text{the edge opposite } v_1\\ E_2(p) &= \operatorname{edge}(v_0, v_1, p) && \leftarrow \text{the edge opposite } v_2\\[8pt] \text{inside} &\iff E_0(p) \ge 0 \ \text{ and } \ E_1(p) \ge 0 \ \text{ and } \ E_2(p) \ge 0 \end{aligned}

Each edge function is zero on its edge's line, positive on one side and negative on the other. It is a half-plane test. A triangle is the overlap of three half-planes, so a point is inside exactly when all three functions agree. In screen space, where y points down, the signs above hold for a triangle wound clockwise on screen. For the other winding all three signs flip, so a rasterizer either flips them (or swaps two vertices) during setup, or culls the triangle as a back face.

Edge functions are linear in x and y. Stepping one pixel right changes E by the constant −(b.y − a.y), and stepping one pixel down changes it by (b.x − a.x). Hardware never recomputes the full formula. It adds constants, and it tests whole blocks of pixels (for example 2×2 "quads" or 8×8 tiles) in parallel.

Which pixels get tested? The simplest strategy is the triangle's bounding box: visit every pixel between the minimum and maximum x and y of the three vertices. For a thin diagonal triangle most of those tests fail, so real GPUs first reject whole tiles at once, but the per-pixel test is the same.

Key idea. "Inside the triangle" means three signs at once. Each edge function is a cheap linear formula, which is why rasterization maps so well onto wide parallel hardware.

STEP 3Pixel centers and the top-left fill rule

The convention in Direct3D 10+, OpenGL and Vulkan is that pixel (i, j) covers the square from (i, j) to (i+1, j+1), so its center is at (i + 0.5, j + 0.5). (Direct3D 9 put centers on integers, which was a classic source of half-pixel offset bugs.)

Meshes are made of triangles that share edges. If a pixel center falls exactly on a shared edge, the test E ≥ 0 passes for both triangles, so that pixel is drawn twice. With blending, the doubled pixel shows up as a visible seam. Switching to a strict E > 0 is no better, because then neither triangle draws the pixel and you get a crack.

The fix is a tie-break called the top-left rule. A pixel center lying exactly on an edge counts as inside only if that edge is a top edge (exactly horizontal, with the rest of the triangle below it) or a left edge (on the triangle's left side). A shared edge is "left" for one of its triangles and "right" for the other, so exactly one of them takes the pixel. In our clockwise, y-down setup, an edge from a to b is top-left when b.y < a.y, or when b.y = a.y and b.x > a.x.

Direct3D spells this rule out exactly. OpenGL and Vulkan require only that a pixel on a shared edge be produced exactly once, and in practice GPUs use a top-left-style convention. To make exact ties reliable, vertex positions are snapped to a fixed-point sub-pixel grid first. Direct3D 11, for example, requires 8 bits of sub-pixel precision.

Key idea. A good rasterizer gives every pixel along a shared edge to exactly one triangle: no gaps, no double hits. That "watertight" property is what lets meshes made of thousands of triangles look like one smooth surface.

STEP 4Barycentric coordinates and interpolation

Covering pixels is only half the job. Each vertex carries data, such as a color, a normal, texture coordinates and a depth, and every fragment needs a value for each of them. The edge functions already computed in Step 2 give us the weights for free. Divide each one by the triangle's total (doubled) area and you get the barycentric coordinates:

area=edge⁡(v0,v1,v2)(twice the triangle’s area)λ0=E0(p)areaλ1=E1(p)areaλ2=E2(p)areaλ0+λ1+λ2=1value(p)=λ0A0+λ1A1+λ2A2(A=any vertex attribute)\begin{aligned} \text{area} &= \operatorname{edge}(v_0, v_1, v_2) && \text{(twice the triangle's area)}\\[6pt] \lambda_0 &= \frac{E_0(p)}{\text{area}} \qquad \lambda_1 = \frac{E_1(p)}{\text{area}} \qquad \lambda_2 = \frac{E_2(p)}{\text{area}}\\[6pt] & \lambda_0 + \lambda_1 + \lambda_2 = 1\\[6pt] \text{value}(p) &= \lambda_0 A_0 + \lambda_1 A_1 + \lambda_2 A_2 && (A = \text{any vertex attribute}) \end{aligned}

Geometrically, λ0 is the area of the small triangle formed by p and the edge opposite v0, divided by the whole area. At v0 itself λ0 = 1 and the others are 0. On the edge opposite v0, λ0 = 0. Inside the triangle all three weights are between 0 and 1. Outside, at least one is negative, which is exactly the inside test again.

For example, at the centroid every λ is 1/3, so with red, green and blue vertices the color there is (0.33, 0.33, 0.33), a dark gray. This screen-space blend is correct for depth (z/w varies linearly across the screen), but texture coordinates and colors on a perspective-projected triangle need perspective-correct interpolation. Chapter 04 shows the fix and the warping you get without it.

Key idea. One set of three weights per fragment interpolates every attribute. The rasterizer computes λ0, λ1, λ2 once and the fragment shader receives smoothly blended inputs.

STEP 5Hidden surfaces: painter's algorithm vs the z-buffer

When triangles overlap, which one should a pixel show? The oldest answer is the painter's algorithm: sort the triangles by depth and draw the farthest first, so nearer ones paint over them. It breaks in two common cases. Triangles that interpenetrate (one is in front at one end and behind at the other) have no correct order. Three triangles that overlap in a cycle can't be sorted either. And sorting by a single number per triangle, such as its average depth, is often wrong even without either problem.

The z-buffer (depth buffer) settles visibility per pixel instead of per triangle. Alongside the color buffer it stores one depth value per pixel, cleared to the farthest value, 1.0. For each fragment the rasterizer interpolates depth with the barycentric weights. In OpenGL's default depth range, window depth is (zndc + 1) / 2, from 0 at the near plane to 1 at the far plane. Then comes the depth test: with the common LESS comparison, the fragment survives only if its depth is smaller than the stored one. A surviving fragment writes its color and its depth. Draw order no longer matters for opaque surfaces.

The z-buffer has a cost: every fragment is still rasterized, and in the simplest pipeline it is shaded before its depth is tested, so hidden fragments waste fragment-shader work (overdraw). Modern GPUs run the depth test before the fragment shader whenever the result can't change. This is called early-z, and it typically requires that the shader not write its own depth or discard fragments. Many GPUs also keep a coarse per-tile depth ("hierarchical Z") to reject whole blocks at once. That's why engines draw opaque objects roughly front-to-back, or render a depth-only pre-pass first. In the demo, Front-to-back lets far fragments fail early.

Edges are still jagged at one sample per pixel. MSAA runs the coverage test and depth test at several sample points per pixel (4× is common) while running the fragment shader only once per pixel, then averages the samples. Chapter 07 covers it in detail. Transparent surfaces are the one place sorting returns: they're drawn after the opaque ones, back to front, with depth testing on but depth writes usually off.

Key idea. The z-buffer turns "which surface is in front?" from a global sorting problem into a tiny per-pixel comparison. It handles interpenetration and cycles for free, and early-z makes it cheap.

RECAPWhat to remember

  • Primitive assembly groups vertices into triangles. Clipping against the near plane must happen before the perspective divide, because vertices with w ≤ 0 project to the wrong side of the screen. A guard band lets GPUs skip most side-plane clipping.
  • Triangle setup computes edge equations, a bounding box and the signed area (winding, used for back-face culling).
  • Three edge functions E0, E1, E2 are linear half-plane tests. A pixel center is inside when none is negative.
  • Pixel centers sit at (i + 0.5, j + 0.5). The top-left rule gives pixels on a shared edge to exactly one triangle: no cracks, no double hits.
  • Barycentric coordinates λi = Ei / area sum to 1 and blend every vertex attribute. Depth interpolates linearly in screen space, while UVs need perspective correction (chapter 04).
  • The painter's algorithm fails on interpenetrating or cyclic triangles. The z-buffer stores per-pixel depth, and the depth test (e.g. LESS) keeps the nearest fragment.
  • Early-z tests depth before shading. Front-to-back order or a depth pre-pass cuts overdraw. MSAA adds extra coverage samples per pixel (chapter 07).

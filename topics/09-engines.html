Game Engine Pipelines

Everything so far happens inside one draw call. A game engine's renderer is the code that decides which draw calls to make, in what order, into which textures, and how to fit all of it into 16.6 milliseconds.

STEP 1CPU-side prep: decide what to draw

A level might contain 100,000 objects, but the camera sees only a slice of them. Every object you send to the GPU costs CPU time to record and GPU time to process, so the first job of an engine's renderer runs on the CPU and is about not drawing things.

Frustum culling throws away objects outside the camera's view volume. Engines test a cheap bounding sphere or box against the six frustum planes; here, in a top-down 2D view, the frustum is a wedge. Occlusion culling removes objects that are inside the frustum but hidden behind something big, like a wall. Real engines do this with precomputed visibility data, GPU occlusion queries, or a low-resolution "hierarchical Z" depth buffer; the demo uses a simple line-of-sight test.

What survives is then sorted. Opaque objects are often sorted by material, so the GPU switches shaders and textures as rarely as possible, or roughly front to back, so the depth test rejects hidden fragments early. Transparent objects must be sorted back to front so blending looks right. Finally, many copies of the same mesh can be merged into one instanced draw call that passes a list of per-instance transforms. The result is a list of commands that gets recorded into command buffers (chapter 08), often on several threads at once.

Key idea. The cheapest draw call is the one you never make. Culling cuts the number of objects; sorting cuts state changes; instancing cuts the number of calls needed for what remains.

STEP 2Render graphs: a frame as a list of passes

A modern frame is not one render. It is a dozen or more passes, each drawing into or computing textures that later passes read. A typical deferred frame goes: depth prepass → shadow maps → G-buffer → SSAO → lighting → sky and volumetric fog → transparents → post-processing (TAA, bloom, tonemapping) → UI.

Wiring these by hand gets fragile fast. At GDC 2017, Yuriy O'Donnell presented Frostbite's FrameGraph, and the idea spread widely (Unreal calls its version the Render Dependency Graph; Unity has a RenderGraph API). Each pass declares which resources it reads and writes, and leaves the details to the graph. Then a compile step:

  • orders the passes by their dependencies;
  • culls passes whose outputs nobody reads, walking backwards from the final image;
  • aliases memory: short-lived ("transient") textures whose lifetimes don't overlap can share the same memory;
  • inserts barriers, the explicit synchronization that APIs like Vulkan and D3D12 require when a texture switches from being written to being read.
Key idea. Passes only say what they read and write. Because the graph sees the whole frame at once, it can schedule, skip, share memory and synchronize automatically, which is far less error-prone than doing it by hand.

STEP 3The frame budget

At 60 frames per second, every frame gets 1000 / 60 ≈ 16.7 ms; at 30 fps, 33.3 ms. Everything above (all passes, plus any ray tracing and post-processing) has to fit inside that, on top of the CPU work. Rendering engineers spend a lot of their time with GPU profilers, moving milliseconds around.

Each pass scales differently. Screen-space passes (G-buffer, SSAO, lighting) cost roughly in proportion to the number of pixels, so rendering at 75% resolution per axis costs about 0.75² ≈ 56% as much. Shadow maps scale with the number of cascades instead. That's why upscalers matter so much: NVIDIA DLSS, AMD FSR and Intel XeSS render at a lower internal resolution, then reconstruct a sharp full-resolution image from several jittered frames plus motion vectors. DLSS and recent FSR versions use neural networks; they usually replace TAA rather than adding to it.

Key idea. A frame is a fixed budget. Every feature buys image quality with milliseconds, and resolution is the biggest lever, which is why reconstruction upscalers are now standard.

STEP 4Unreal 5 and Nanite-style cluster LOD

Unreal Engine 5 uses deferred shading by default (a forward renderer is available too, often used for VR). Its three headline systems, as Epic describes them:

  • Nanite, "virtualized geometry": meshes are split into small clusters of triangles (around 128 each) arranged in a hierarchy of levels of detail. Each frame the GPU picks, per cluster, the coarsest version whose simplification error would be smaller than about a pixel on screen. Tiny triangles are rasterized by a software rasterizer running in compute shaders, because hardware rasterizers are inefficient with pixel-sized triangles.
  • Lumen, dynamic global illumination and reflections: bounced light is traced against simplified scene representations (such as signed distance fields and screen-space data), with hardware ray tracing as an option.
  • Virtual Shadow Maps: very high-resolution shadow maps (Epic cites 16k × 16k) split into pages, where only the pages actually needed on screen are rendered and cached between frames. They are designed to pair with Nanite's detail.

Here's the core of the Nanite idea in 2D. The "mesh" is a terrain line made of 256 segments (our stand-in for triangles), grouped into clusters of 16. Each coarser level has half as many clusters, and each cluster still has 16 segments, so it covers twice as much ground with half the detail. Every cluster stores its error, the largest distance between its simplified shape and the full detail. Projected onto the screen, error ≈ error × focal length ÷ distance, in pixels. If that's below the threshold, the cluster is drawn; otherwise its two children are tested instead.

Key idea. Instead of choosing one LOD for a whole object, cluster LOD picks detail per small patch, by how many pixels its error would cover. Geometry cost then tracks screen resolution, not how detailed the source mesh is.

STEP 5Rasterization vs ray tracing, and the hybrid frame

Rasterization asks, for each triangle, "which pixels does this cover?" It projects geometry towards the camera, which is very fast but only answers questions about what the camera sees directly. Ray tracing asks, for each pixel, "what does this ray hit first?" It can follow a ray onward to a light (shadows) or bounce it off a mirror (reflections). Testing every ray against every triangle would be hopeless, so the scene is stored in a bounding volume hierarchy (BVH): a tree of boxes. A ray that misses a box skips everything inside it.

DirectX Raytracing (DXR) and Vulkan's ray tracing extensions expose this on GPUs with hardware support: the driver builds the BVH ("acceleration structures"), and the hardware speeds up box and triangle tests. Games almost always use a hybrid: rasterize the primary view into a G-buffer as usual, then trace a small number of rays per pixel for shadows, reflections or GI. Those few rays give a noisy result, so a denoiser blends results across neighboring pixels and previous frames.

Key idea. Raster is the fast way to find what the camera sees; rays are the flexible way to ask everything else. A BVH makes rays affordable, and denoisers make a few rays per pixel enough.

STEP 6Engines compared, and building your own pipeline

Unity's Scriptable Render Pipeline (SRP) moved the renderer from engine internals into C# you can read and replace. Unity ships two: the Universal Render Pipeline (URP), built to scale from phones to consoles, and the High Definition Render Pipeline (HDRP) for high-end PC and console. HDRP has been built on a render graph internally for several versions, and in Unity 6 URP uses the RenderGraph API by default. Godot 4 offers three renderers: Forward+ (clustered forward lighting for desktop), Mobile (a simpler forward renderer for phones and tablets) and Compatibility (OpenGL-based, for old hardware and the web).

You don't need a AAA team to use these ideas. Suppose you want a stylized pixel-art look for a 3D game. As a render graph, it's just a few passes:

// pseudocode, engine-agnostic
lowRes  = createTexture(screenW / pixelSize, screenH / pixelSize)
pass "scene":     write lowRes.color, depth, objectId  // tiny target
pass "outline":   read objectId -> write lowRes.color  // dark edges
pass "palette":   read/write lowRes.color  // nearest palette color
pass "upscale":   read lowRes.color -> write backbuffer (nearest)
pass "UI":        write backbuffer at full resolution

In Godot that might be a SubViewport with nearest filtering plus a screen shader; in Unity URP, a low-resolution render texture plus a Renderer Feature. A common extra trick is snapping the camera to whole low-res texels so the image doesn't shimmer as it moves. Try each pass below.

Key idea. A custom pipeline is just your own render graph: choose the targets, the passes and their order. Pixel art is "render small, post-process, upscale with nearest filtering."

RECAPWhat to remember

  • The CPU side of a renderer culls (frustum, occlusion), sorts (by material, by depth, transparents back to front), batches and instances, then records command lists.
  • A render graph has passes declare their reads and writes. The graph orders passes, culls unused ones, aliases transient memory and inserts barriers for you (Frostbite FrameGraph, GDC 2017).
  • A typical frame: depth prepass → shadows → G-buffer or Forward+ → SSAO → lighting → sky/volumetrics → transparents → TAA, bloom, tonemap → UI, all within about 16.7 ms at 60 fps.
  • Resolution is the biggest cost lever; DLSS, FSR and XeSS render fewer pixels and reconstruct the rest.
  • Unreal 5 is deferred by default, with Nanite (cluster-hierarchy LOD chosen by screen-space error, software rasterization of tiny triangles), Lumen GI and Virtual Shadow Maps. Unity offers URP and HDRP through SRP; Godot 4 offers Forward+, Mobile and Compatibility.
  • Hybrid rendering rasterizes primary visibility and traces rays through a BVH for shadows, reflections and GI, then denoises.
  • Your own pipeline, such as a pixel-art one, is the same idea at small scale: a low-res target, a few post passes, and a nearest-neighbor upscale.

The Programmable GPU

STEP 1From fixed function to programmable

The first 3D hardware was a fixed-function pipeline: the math from chapters 01–03 was baked into silicon. You could turn features on and off and set parameters (a light's direction, a fog color, a texture blend mode), but you couldn't write new math. If you wanted a lighting model the hardware didn't have, you were out of luck.

Over roughly fifteen years each stage gave way to small programs called shaders. Pick an era below and watch which stages become programmable. Notice what never changes: rasterization, depth testing and blending are still fixed hardware today, because they're simple, run constantly, and are fastest as dedicated circuits.

Key idea. "Programmable" moved through the pipeline from the vertex end to the pixel end, then the separate units merged into one pool of general cores. The steps in between (rasterize, depth, blend) stayed fixed.

STEP 2The whole logical pipeline

Here's the pipeline as an API like OpenGL, Direct3D or Vulkan describes it. It's the logical order: real hardware overlaps and reorders work, but the results must look as if every stage ran in this order. Filled boxes are programmable (you write a shader); outlined boxes are fixed (you can only configure them).

A draw call feeds vertices in at the top. The vertex shader runs once per vertex and must output a clip-space position. Fixed hardware then assembles triangles, clips them, does the perspective divide and the viewport transform, and rasterizes them into fragments (chapter 02). The fragment shader runs once per fragment to compute a color, and the output stages test depth and blend the result into the framebuffer.

Two kinds of optional extras exist. Tessellation (hull/control shader → fixed tessellator → domain/evaluation shader) subdivides patches into many triangles, and the geometry shader can emit or delete whole primitives. More recently, mesh shaders replace the whole vertex front end with a compute-style stage that outputs small batches of triangles called meshlets.

STEP 3Write a fragment shader

Time to program the GPU directly. The canvas below is a real WebGL pipeline drawing one rectangle (two triangles) that covers the whole canvas. The vertex shader is trivial: it passes four corners straight to clip space. All the interesting work happens in the fragment shader, which runs once for every pixel of the canvas: about 300,000 times per frame for a 600×500 canvas.

Your shader gets three uniforms, values that are the same for every fragment in a draw: u_time in seconds, u_resolution in pixels, and u_mouse (the pointer position in pixels, origin bottom-left like gl_FragCoord). Its job is to write gl_FragColor. Edit the code and it recompiles as you type. If the code won't compile, the driver's error message appears below the editor.

Key idea. A fragment shader is a function from "where am I + uniforms + interpolated inputs" to a color. It can't see its neighbours or remember the previous pixel. That independence is exactly why the GPU can run hundreds of thousands of copies at once.

STEP 4Thousands of threads, marching in lockstep

How does a GPU run one shader 300,000 times per frame? It has thousands of simple arithmetic lanes and groups threads into bundles that share one instruction stream: warps of 32 threads on NVIDIA, wavefronts of 64 (or 32 on newer designs) on AMD. Each clock, the scheduler issues one instruction and every lane in the warp executes it on its own data. This is called SIMT, single instruction, multiple threads.

The catch is branches. If some lanes take an if and others take the else, the warp can't do both at once. It runs the if path with the other lanes masked off, then the else path with the first group masked off. This is divergence: masked lanes do no useful work. If all 32 lanes agree, the untaken path is skipped entirely and nothing is lost.

Fragments are also packed in 2×2 quads. Functions like dFdx and the automatic mip selection in texture2D (chapter 04) compare values between neighbouring pixels, so all four pixels of a quad must run, even ones outside the triangle (those are "helper" lanes). Thin triangles waste many lanes this way.

Key idea. A branch costs the sum of both paths whenever lanes in the same warp disagree. Branches that are uniform across a warp (or across the whole draw, like one based on a uniform) are cheap. Branches that differ pixel by pixel can be expensive.

STEP 5Overdraw and early-z

Each pixel ends up showing one surface, but many surfaces may have been shaded there first. Every time an opaque fragment is shaded and later covered by a nearer one, that shader work is wasted. This is overdraw, measured as fragment-shader invocations per visible pixel.

Logically the depth test comes after the fragment shader. But if a shader doesn't change its fragment's depth (and doesn't use features like discard that complicate things), the GPU can test depth before shading. This is early-z, and it skips the shader for hidden fragments. It only helps when nearer surfaces are already in the depth buffer, so engines sort opaque objects roughly front to back, or run a cheap depth-only pre-pass first. Transparent objects are different: they must be blended back to front, so they always pay full overdraw.

Key idea. Early-z turns "draw nearest first" into real savings: hidden fragments are rejected before the expensive shader runs. Drawn back to front, every layer passes the depth test, and you pay for every one.

RECAPWhat to remember

  • GPUs went from fixed function (switches and parameters) to programmable shaders (around 2001) to unified shader cores (around 2006) that run any shader type, plus compute.
  • Logical pipeline: input assembler → vertex shader → (tessellation, geometry shader) → primitive assembly & clipping → rasterizer → fragment shader → depth/stencil → blending.
  • You write the vertex and fragment shaders (and optional stages); assembly, clipping, rasterization, depth and blending stay fixed but configurable.
  • Mesh shaders (with optional task/amplification shaders) replace the vertex front end with compute-style workgroups that output meshlets.
  • Shaders run in warps/wavefronts of 32 or 64 lanes (SIMT). Divergent branches run both paths, and fragments run in 2×2 quads so derivatives work.
  • Overdraw wastes fragment work. Early-z plus front-to-back sorting (or a depth pre-pass) skips hidden fragments.
